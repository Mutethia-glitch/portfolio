SentinelX is a cybersecurity incident detection and response system for IPHYN. It brings together telemetry normalization, explainable security rules, analyst investigation and controlled, accountable response.

01 / CORE STORY

The challenge

Security telemetry can be fragmented and noisy. An analyst needs more than an alert — they need enough context to understand the event, distinguish risk from status, and make an accountable decision.

The system also needs to respect a hard security boundary: data and user actions belonging to one company must not be accessible from another company.

02 / CORE STORY

The system

The core workflow is event ingestion → normalization → deterministic detection → alert → correlation → incident → investigation → controlled response → resolution → reporting.

Fifteen canonical detection categories are supported when authoritative evidence is available. Machine-learning anomaly output is an optional supporting layer; it never replaces the explainable deterministic rules. The interface helps analysts understand what happened and act without hiding the underlying evidence.

03 / CORE STORY

Engineering choices

PostgreSQL stores incident and evidence records. Role-based access control restricts sensitive actions. Separate runtime and database boundaries enforce isolation between companies.

Important security and administrative actions are attributed through audit records. Response is deliberate and controlled; this is not a destructive automated attack-remediation platform. Validation covers the full event-to-resolution workflow and cross-tenant boundaries.

04 / CORE STORY

What I learned

Explainability and safety are design requirements, not polish. A great detection engine should make a human decision easier to investigate, rather than producing an opaque verdict.

This project is intentionally a focused detection-and-response system, not an antivirus or an enterprise SIEM replacement.
